# Integration tests (Step 6)

Every generated endpoint ships with its tests (house-review lenses.md TEST-01…18). **Follow the
golden classes**: `~/.claude/skills-reference/src/test/java/com/example/app/todo/TodoIntegrationTest.java`
(cursor list, state action, child of a list) and `TodoListIntegrationTest.java` (offset list,
unique name, dropdown). Generate `{{testRoot}}/<app path>/EntityNameIntegrationTest.java`:
- extends `{{testBase}}` (one shared Spring context; **never** `@MockitoBean` or
  `@TestPropertySource`, which start another context);
- uses the base's client and helpers (`newUser()`, `signIn(account)`, `newAdmin()` and
  `newUserWithRole(role)` with the metadata or media piece, `getAs`/`postAs`/…, `read`, `sql`,
  `statistics()`, `randomIds(n)`, `race(...)`, `awaitLockWaiters` with `lockWaitDeadline()`,
  `awaitLatch`, `awaitResult(future)`, `createsHeldAtTheirInsert` and `writesHeldWhileTheParentWaits`
  (row 23), `newExecutor()` for a test's own threads (never `Executors.*`
  directly: with tenancy its threads run in the test tenant); with media `uploadPolicyOf`,
  `setUploadPolicy`, `restoreUploadPolicy`; with tenancy `newTenant()`, `newUserIn(tenant)`, `newUserIn(tenant, role)`,
  `platformToken()`, `testTenant()`);
- with tenancy the tests read as without it: they run inside one test tenant of the run (services and
  jobs called directly included), and `jdbc`/`sql` see its tables. A class about tenancy itself, or
  testing a platform-wide job, is `@WithoutTestTenant`: no scope, each request's token names its tenant;
- fixtures several classes share go by what they serve: **a piece's** helpers (media's upload
  policies, metadata's stored values) live in `{{testBase}}` itself, beside the piece's markers, as the
  golden base does; **the domain's** (an account linked to a record, a manager, a role beyond ADMIN) go
  in a project base extending `{{testBase}}`; a new role brings its `new<Role>()` there (REST-25). A
  fixture kept beyond one test caches the account and calls `signIn` on use, never a cached access
  token (it expires after `app.jwt.access-token-ttl`, at most 15 minutes).

**Shipped guards** (core, run under every test of the project): `TransactionGuards` fails a test whose request
leaves changes in a read-only transaction, opens a write transaction on a GET, or calls the object store or an
HTTP API inside a transaction; `EndpointContractIntegrationTest` walks every served endpoint. A generated
entity's tests need no duty for these; they only have to reach every write path (rows 1-13), so the guards
see it. A project's own remote client is added to `TransactionGuards.isRemoteClient`. Doc drift is checked
for free too (REST-20): `ObservedOutcomes` fails a test whose response the operation's docs don't list, and
`ApiDocsDriftIntegrationTest` an unknown code or a restated bound; so the generated API interface has an
`@ApiResponse` for every status its tests reach, naming every `errorCode` that status carries, and no
description repeats a `@MaxLength`/`@Size`/`@Min`/`@Max` bound. The test base's `support` package serves
test-only handlers (`HostileInputProbeController`, under `/api/{version}/hostile-input-probes`): a project
test that walks the handler mappings against a table of its own skips the handlers whose bean type is in that
package (`handler.getBeanType().getPackageName().equals(IntegrationTest.class.getPackageName())`).

## Conventions
The test rules are house-review's TEST-xx (lenses.md): one behaviour per test with `@DisplayName`,
own data, shared state reset with `@ResourceLock`, today computed once (TEST-07); setup asserts its
2xx and direct fixtures go through `sql(...)` (TEST-10); every refusal asserts its `errorCode`, on
every call (TEST-08); an absence follows a presence (TEST-16); order fixtures that differ under every
order (TEST-10); query parameters with special characters through `.param(...)`, and a 403 test with
a valid body (TEST-07). A validation refusal asserts where and why (ERR-07): `$.errors[0].pointer`
`"#/name"` (a body field) or `$.errors[0].parameter` `"size"` (a query parameter), and
`$.errors[0].detail` with the configured number (`"must be at most 100 characters"`); among several,
`$.errors[?(@.pointer == '#/name')].detail`. No `var`; JSON as text blocks or fixture helpers.

**Shared tables** (a catalogue, admin-managed types, employees: no `owner_id`, SKILL.md Step 1): the
shared database holds every other test's rows, so each list test scopes its calls by a filter only
its own rows match (a fresh parent id, a unique `query` token), every call of it, the filter's own probes
included (a case-insensitivity check searches with the token, not the whole table), and never asserts a page's absolute
contents or totals, nor that a table is empty; row 15 doesn't apply (nobody owns the record), and the
golden "a list shows only yours" test has no counterpart: drop it (with tenancy, the
`TenantIsolationIntegrationTest` covers who sees what). Row 14
carries the access decision: a plain USER gets 403 `ACCESS_DENIED` **with a valid body** on every
write (and on every read the decision restricts), the record unchanged; the writing role succeeds
(golden `MetadataIntegrationTest.onlyAdminsReachTheApi`, `UploadPolicyIntegrationTest`).

**Fixtures in row mode** (`{{tenancy}}` = `row`): another tenant's rows through `sqlIn(tenant, …)` (the
test base: its own transaction, on a connection told that tenant), each insert naming its `tenant_id`; never
`set_config('app.tenant_id', …)` by hand (TEN-31 reserves it for the hook). A `@BeforeAll` that writes
through a `TransactionTemplate` of its own calls `testTenant()` first: created inside that transaction the
tenant's after-commit provisioning never runs, and it stays PENDING (`sql()` does it for you).

## Index tests (row 28)

Every offered order has a matching index, the scope first and the id last; a filter has one only when the
developer asked for it (SKILL.md 4.1, DATA-10: the developer's call, recorded in *Decisions per entity*). An
index test checks **the indexes that exist**, never a plan per filter combination, with three kinds of
assertion, and nothing about costs:
1. **Each index the entity has**: one parameterized test over `(what it serves, index name)` pairs,
   `QueryPlan.indexExists` for each: every order, each requested filter index under every order, each range
   filter under its own order (the order's index), each second step's and each parent's delete-side foreign key
   check, the unique and exclusion constraints, each job's lease, each purge's batch (row 34). The `ids` lookup
   rides the primary key, which always exists: no row unless the rules ask for one.
2. **The first page is planned on its index**: per list (a dropdown is a list of its own), one `EXPLAIN` of
   the first page in the default order, written as the repository issues it (same select list, predicates,
   order, `limit`; `size + 1` for a cursor list): `QueryPlan.explain(jdbc, transactionManager, sql,
   parameters)` plans it without running it, with sequential scans, bitmap scans and sorts off (on a test
   database's small tables, or for a scope the statistics put at a row, the plan would otherwise turn on the
   data), and the test asserts `doesNotContain("Seq Scan")` and that
   `QueryPlan.indexesScanned(plan)` holds the expected index; when the default first page carries an equality
   filter (a dropdown's ACTIVE), the filter's index or the order's index (golden `TagIndexIntegrationTest`). A scope id that matches nothing
   is enough: no seed, the plan comes from the statement. A requested filter index gets the same check for
   the first page under that filter.
3. **A later batch seeks on its index**: per cursor list (each dropdown included, its `DESC` too), the batch
   after a cursor as the repository issues it, `(<sort keys>, id) > (:key, :id)` (`<` for `DESC`): planned on
   the order's index, the row comparison among the scan's `Index Cond` lines (an OR-form seek, or one the
   index can't take, shows as a `Filter`; golden `TodoIndexIntegrationTest.aLaterBatchSeeksOnItsOrdersIndex`).

Golden: `TodoIndexIntegrationTest`, `TagIndexIntegrationTest`, `TimeEntryIndexIntegrationTest`,
`PlanIndexIntegrationTest`, `MediaFileIndexIntegrationTest`, the tenancy overlay's
`TenantMemberIndexIntegrationTest`. With row tenancy each first-page statement names its tenant, `and
tenant_id = :tenantId` with the test tenant's id, as Hibernate adds it to the repository's query (TEN-32)
and as TEN-37 asks of native SQL: the policy is the fallback, never the filter (golden: the `tenancy-row`
blocks of those classes); the dependency statistics (TEN-33) get an existence check (golden
`OwnerTenantStatisticsIntegrationTest`).

**No claims a test doesn't assert**: no javadoc saying a cell "fails without its index", no "reads N times
its bound", no seed shaped to make a missing index expensive. What the data looks like in production is not
known here. **Extension point (a use case, not generated):** a project with a known data distribution or a
latency target adds its own `EXPLAIN (ANALYZE, BUFFERS)` tests on a seed that models it.

Which filters and orders are offered, and under which order, is DATA-10's rule (SKILL.md 4.1).

Test method names may follow the golden classes. When the golden tests, this table and a house-review
rule disagree, SKILL.md's precedence decides (rules, then this table, then golden).

**A record listed at several reaches** (`/mine`, `/team`, the bare collection, REST-08) gets every list row (16,
16b, 17, 21, 24: the walk, the statement count for one row, a full page and a batch after a cursor, each sort in
both directions) **per list**, not on one of them: each list has its own query, scope and plan.

## Upgrading a used database

A changeset that backfills or changes existing rows (a new `NOT NULL` column, a display number for the
rows already there, a per-tenant seed for the tenants that exist) is tested on a database that already
holds the previous release's data, never only on an empty one: on an empty database a backfill that
starts a counter at 0 instead of the highest number, or reaches only the ACTIVE tenants, passes every test.
The test base's `PreviousReleaseDatabase` (core) builds that database for the whole run when
`app.test.upgrade.previous-release` names the release in production (the highest changeset number of
each range it shipped, `<pieces>[,<project>]`: the pieces own 0001-0099, the project 0100 and up, and a
piece's changeset added since the release runs after the project's, so one number can't say what shipped;
`28,105`, or `28` while the project has none of its own; the review profile's `shippedRelease` records it,
updated at each release, and both skills read it as what has shipped, DATA-13): Liquibase applies the changesets up to the
first one the release didn't ship, `src/test/resources/db/upgrade/previous-release-seed.sql`
fills them as a used database holds them, then the application's own run applies the newer changesets
(schema per tenant: each provisioned tenant's schema at that release too, with
`previous-release-tenant-seed.sql`, which the deploy-time `TenantMigrations` then brings up). Every test of
that run works on the upgraded database; `UpgradeFromPreviousReleaseIntegrationTest` (row 30) asserts the
backfills. Run it as `./mvnw verify -Dapp.test.upgrade.previous-release=<pieces>,<project>`.

The seed is realistic rather than tidy: several accounts and one with most of the rows, statuses skewed
as they are in production, every table filled, with tenancy tenants in every status (each with what that
release gave it: the provisioned ones their seeds, a PENDING one none), a member in two tenants and one who
left. Write it against the previous release's tables only, with fixed ids for the rows the test reads.
**When a release ships**, raise the number and add the new tables' rows to the seed. **Before upgrading
a live database**, also run the migration once against a restored copy of it (the runbook's upgrade
section): the seed models production, the copy is production.
